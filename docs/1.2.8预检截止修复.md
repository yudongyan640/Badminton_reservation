# 1.2.8：在途预检不再拖过计划触发点

2026-10-23。用户仅授权修复上一轮审查的问题2；不提交真实预约、不自动启用任务。

- 原缺陷：预检在零点前1秒启动、2.5秒后失败，旧调度还会再等一次轮询。多步预检各自使用2.5秒时，总耗时也会超过剩余时间；页面就绪等待原先未计入超时。
- 修复：各阶段预检共用单调时钟截止点，在计划触发前100毫秒停止；阶段2另有整轮2500毫秒上限。每步只使用剩余预算；新校时改变触发边界时也重新裁剪。预算耗尽不再发起后续预检。
- 浏览器：页面就绪、导航及接口请求共享调用预算；较早阶段允许在预算内启动浏览器预热，短预检不再启动新的浏览器，登录窗口仍可通过原入口打开。普通无显式短超时的操作保持原流程。没有用Promise.race遗留继续运行的预检请求。
- 预检失败返回后立即重新计算触发时间与期限，已到点则在同一轮执行；未到点按剩余等待调度。原40毫秒余量、保守时间判断、单在途、300毫秒间隔、20次/15秒窗口及提交前落盘均不变。
- 新回归先复现失败、再验证通过：跨过触发点后同轮执行；设置与查询共享剩余预算；时间不足不启动预检；已成功查询结果在预算末尾保留；零点前11秒首次调度也受截止约束；驱动排队耗尽预算后不再发请求。Edge本地夹具另外验证页面就绪耗尽预算后不再发送settings请求。
- 全套92项测试、类型检查、Edge本地夹具与日历界面检查为交付验证项。仅模拟与只读检查，真实创建/取消预约请求为0。网络、操作系统调度和后续预约查询仍可能耗时，本版不承诺绝对准点或必抢到。
- 范围保留：1.2.7的cachedFresh查询失败后records=[]策略未改。该策略可能漏查已存在的本人预约，需要用户另行授权修复；本版不能视为整体防重复风险已解决。
