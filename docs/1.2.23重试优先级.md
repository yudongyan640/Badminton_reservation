# 1.2.23 重试优先级（本地重选的任务先发）

日期：2026-11-25

## 背景

11-25 零点，账号2 任务 `64af6c1e`（2026-11-26 21:00–22:00 场2）首刀 +26ms（wire）发出，463ms 返回“您的会议与赵伟鹏发起的会议0(2026-11-26 21:30~22:00)冲突”。程序在 +533ms 就用缓存完成本地重选（21:00–21:30，只花 9ms），但真正的第二次提交直到 +1533ms 才发出（服务端触发 +1494ms），447ms 创建成功，最终只保留 30 分钟。

原因不在“选得慢”，而在“排队”：同批的 `115cfde3`（20:00–21:00 场2）首刀 +16ms 收到一次 transient，按 `ZERO_TRANSIENT_DELAYS[0]=0` 在 +533ms 发出重试，998ms 才返回；首波之外严格单在途，唯一的提交位置被它占着，21:00 这条已经选好新时段的任务只能排在后面。竞争激烈时，晚 1 秒足以丢掉剩余时段。

## 改动

只改重试阶段的遍历顺序，不改任何请求次数、节奏或安全边界。

- `src/engine.ts`：`ExecContext` 新增 `reselectReady:boolean`（初始 `false`）。
- `processResult`：首轮冲突（`conflictsSinceRefresh<1`）用缓存本地重选后，若 `ctx.choices` 非空，置 `ctx.reselectReady=true`，再 `return` 进入重试。
- `executeTasks` 重试阶段：每轮先遍历 `reselectReady` 的任务（相互之间保持创建顺序），再按创建顺序遍历其余任务；`while` 条件、15 秒/20 次上限、`notBefore` 退避、`wait` 计算均不变。
- `submitAttempt`：真正发出前（`sleep` 之后）清除 `ctx.reselectReady`；若这次又冲突，下一轮冲突会重新判定，不会永久插队。

单在途仍然成立：`for` 循环里 `await this.submitAttempt(ctx)`，下一条必须等上一条响应返回；`submitAttempt` 的 100 毫秒全局下限与 20 次/15 秒窗口不变。

## 不改动

- 零点触发点、`EARLY_GUARD_MS`、首波并发、`MAX_PARALLEL_FIRST_SHOTS`、零点刷新限时、`ZERO_TRANSIENT_DELAYS`；
- 响应分类、冲突文案与区间校验、`not-open` 识别、`unknown` 冻结；
- 提交前落盘、结果核对、部分成功即停、未知先核对暂停；
- 不增加任何网络请求，事件与诊断字段不变。

## 测试

`tests/engine.test.ts` 新增 1 项：

- 两条时段重叠、场地不同的任务（场1/场2，19:00–20:00）：a 首刀 transient，b 首刀冲突（19:00–19:30 被占）并本地重选出 19:30–20:00。断言重试顺序为 场1 → 场2 → 场2(19:30–20:00) → 场1，即 b 的重选补发先于 a 的 transient 重试；a 完整成功，b 只剩 30 分钟按部分成功停止。

结果：`npm run check` 通过；`node --test --test-isolation=none --test-concurrency=1 "tests/*.test.ts"` 131 项全部通过。FakeSite，无真实创建/取消，实际预约写转发为 0。

## 风险与未验证

- 真实零点尚未验证；预期只影响“同一批多条任务同时需要重试”时的顺序，单任务、首波并发行为不变。
- 需要观察：`conflict-local-reselect` 之后的下一次提交是否从约 1 秒缩短到约 100 毫秒；相邻提交仍应 ≥100 毫秒；是否出现新的拒绝形态或更密集的 `资源分配错误`。
- 出现未识别响应仍先核对并暂停；真实效果不保证抢到。

## 生效

升级后需重启两个实例（38321/`data`、38322/`data-b`），并在专用 Edge 重新“检查登录”；`data`/`data-b` 无需迁移。
