## 零点触发点前移与过早提交兜底（1.2.5）

2026-10-22 00:00真实记录：目标10-23 20:00–21:30；首次请求在本机开放后126毫秒、按锚定服务器时间约138毫秒发出（余量80毫秒+校时误差57毫秒+约1毫秒调度），128毫秒后收到“资源分配错误,请十秒后重试！”。1.2.4分支在0.8秒后于+1.31s换场重试（场地2 20:00–21:00），再次收到同错误；1.6秒后刷新发现目标内已无空闲，失败且未冻结。

- 释放余量由80毫秒降为40毫秒（`RELEASE_GUARD_MS`），保守判定`min(本机墙钟, 服务器时间-误差下界)`与单调时钟锚不变。按本次实测误差57毫秒计算，触发点由约138毫秒前移到约98毫秒（40+57+约1）。

- 临时资源分配错误后的重试间隔由0.8/1.6/3.2/4秒改为0.15/0.6/1.5/3秒，仍受15秒窗口和20次上限约束，且每次重试前先只读核对本人记录。

新增过早提交兜底：HTTP200、code200、data为空、文案严格为“不能预订超过2天的会议”（2026-10-20零点真实记录，当时未创建并由用户手动补约），且规则绑定当前场馆时，判定kind=not-open、已确认未创建，按300毫秒间隔立即重试，不再冻结。若40毫秒余量下偶然过早提交，可在约350–450毫秒内恢复，而不是丢失整个任务。

## 稳健性修复（1.2.6）

外部代码评审（对照1.2.5）提出的问题经复核后处理如下，本轮未改变零点触发时机（40毫秒余量保留，等待真实wire时间数据再评估）。

- **核对失败不得继续提交**：1.2.5在临时资源分配错误后执行`try{list()}catch{}`，查询失败会沿用旧缓存继续提交，削弱防重复。1.2.6改为：查询失败先补查一次（约200毫秒后），仍失败即按“临时错误后无法核对本人记录，已停止本次提交”结束本轮（不冻结，因响应已明确未创建），与冲突分支的“刷新失败即停止”保持一致。
- **校时采样必须有截止时间**：1.2.5串行5次采样，每次`api`超时8秒，理论最坏可从零点前10秒拖到零点后30秒以上。1.2.6改为：以保守剩余等待计算预算`min(2000ms, remaining-1500ms)`，不足500毫秒直接跳过采样；单次请求超时改为`clamp(剩余预算, 500ms, 4000ms)`；预算用尽立即用已采到的最优样本返回；预算计时使用单调时钟`performance.now()`，不受系统墙钟调整影响。

## 同一时段两块场地与多任务批次（1.2.13）

需求（2026-11-02）：用户希望在零点同时预约同一时段的两块场地（例：场地1 19:00–20:30、场地2 19:00–21:00）。原实现的任务模型是“一个日期+一个连续时段+场地优先序列”，`courtPriority`是备选顺序而非“两块都要”；且`Engine.arm`对同模式、活跃、时段重叠的任务一律拒绝，`execute`提交前只要查到本人任意重叠预约就停止。用户点击启用时看到的是本机提示“与已有任务时段重叠，请取消重复任务”，不是网站拒绝。

实现（本机调度层）：

- **启用校验**：仅当“时段重叠且两条任务的场地集合有交集”时拒绝。两个单场地任务（一条只锁场1、一条只锁场2）允许同一时段分别启用；任一场地备选任务（`[1,2]`）仍按重叠拒绝，避免两块都落到同一场地。
- **本人重叠范围**：提交前及冲突/临时错误后的“本人已有重叠预约”判断只检查本任务目标场地；另一块场地的同时段本人预约属于多场地同时预约的预期结果，不再阻止本任务；目标场地有本人重叠记录时仍停止。
- **同轮批次与交错首发**：同一`tick`内所有到点任务一起执行（原实现执行一条就`break`，第二条会晚约1秒）。每条任务先各提交第一刀（按创建顺序），再处理结果、重试与核对；第二条只等第一刀响应+300毫秒，不会被第一条的核对/重试拖到+3秒级。
- **节奏与窗口**：提交节奏从“任务内300毫秒”改为“跨任务全局300毫秒且单在途”；每条任务仍有独立的20次/15秒窗口（从各自开始计时），第一条不会吃掉第二条的次数。
- **预检去重**：同账号、同日期、3秒内的预检结果（设置快照+占用）复用，避免两条任务在零点前把请求量翻倍；超过时效仍重新查询。
- **冻结语义**：同批一条任务结果不明只暂停账号后续任务，同批另一块场地继续提交（用户明确要求“另一条不停”）；两条都结果不明时都保持`unknown`，`freeze`保留一条作为账号暂停锚点，逐条核对/确认后转移或解除，界面显示待确认任务数量。批次之外的任务仍按原规则被暂停。

## 首波并发（1.2.21）

2026-11-20，用户要求同一账号的多个任务在 0 点同时启动：原实现第二条要等第一条 POST 完整返回才发首刀（零点常见 0.2–0.6 秒），且“完整时段冲突→刷新→再抢剩余时段”期间剩余时段容易被他人抢走。

- 范围：只有同一批到点且**时段互不重叠**的任务才并发，按创建顺序取前缀，最多 2 条（`MAX_PARALLEL_FIRST_SHOTS`）；遇到第一条时段重叠的任务即停止并发，其余全部串行。时段重叠（含同一时段两块场地、任一场地备选）仍严格串行，因为平台按账号拒绝同一时间的第二个会议。
- 实现：`engine.executeTasks` 用 `planFirstWave()` 划分首波/串行；首波以 `Promise.all` 调 `submitAttempt(ctx,true)`，`parallel=true` 跳过 100 毫秒节流且不等待彼此响应；首波结束后串行补发其余任务，随后统一处理结果；重试/核对仍单在途、≥100 毫秒、每条任务 20 次/15 秒。首波任务写 `first-wave-parallel` 事件，便于在 events 中核对两条是否同刻发出。
- 不改：响应形态、冲突校验、提交前落盘、未知先核对暂停、部分成功即停、零点复查、预检去重。
- 回归：`npm run check` 通过；`node --test --test-isolation=none --test-concurrency=1 "tests/*.test.ts"` 128 项通过（新增 2 项：时段不重叠的两条任务在任何响应返回前都已发出首刀；时段重叠的两块场地仍串行）。FakeSite 无真实创建/取消，实际预约写转发 0。
