# 1.2.21 首波并发（时段不重叠的多任务同时开抢）

## 背景

用户在同一账号下建多条任务（如 19:00–19:30、19:30–20:00）时，希望 0 点两条任务“同时启动”。1.2.20 及以前的实现里，`executeTasks` 的首发是串行的：

```ts
for(const ctx of contexts){ await this.submitAttempt(ctx); }
```

第二条要等第一条 POST 完整返回后才发首刀；100 毫秒节流此时早已满足，所以第二条实际晚的是“第一条的响应时间”（零点常见 0.2–0.6 秒）。用户遇到的问题是：一条 60 分钟任务被冲突拆成两段时，要经历“完整时段→冲突→刷新→抢剩余时段”，刷新和重选期间剩余时段可能已被他人抢走；拆成两条任务本可并行争取，但串行首发让第二条也晚了约一个响应时间。

## 改动

- `src/engine.ts` 新增常量 `MAX_PARALLEL_FIRST_SHOTS=2`。
- 新增 `planFirstWave(contexts)`：按创建顺序取前缀，一旦遇到与已选任务**时段重叠**（`overlaps`）或已达上限 2 条就停止并发，其余任务全部回到串行。这样保持“按创建顺序”的可预期性，也避免把可能触发平台“同一时间有其它会议”的两条请求并发发出。
- `submitAttempt(ctx,parallel)`：`parallel=true` 时跳过 100 毫秒节流（首波内两条同时发出），其余路径完全不变。
- `executeTasks` 的首发阶段改为：首波用 `Promise.all` 并发调 `submitAttempt(ctx,true)`，互不等待响应；首波全部返回后，再按创建顺序串行补发其余任务的第一刀；之后统一处理结果与重试，最后逐条核对（`verify`）。
- 首波任务写 `first-wave-parallel` 事件，便于在 `events.ndjson` 核对两条是否同刻发出。

## 边界（保持不变）

- 首波只对**时段互不重叠**的任务开放；时段重叠的任务（含同一时段两块场地、任一场地备选）仍严格串行，因为平台按账号拒绝同一时间的第二个会议（11-03 真实零点证据）。
- 首波之外的所有提交（冲突重试、临时错误重试、核对）仍严格单在途、两次提交起始间隔≥100 毫秒、每条任务 20 次/15 秒窗口。
- 提交前 `submitting`+基线落盘、响应形态与冲突校验、未知先核对暂停、部分成功即停、零点复查、预检去重均不变。
- 每条任务的首刀各算一次 `attempts`，不会因并发而少算或多算。

## 测试

`tests/engine.test.ts` 新增 2 项：

1. 时段不重叠的两条任务（19:00–19:30、19:30–20:00，场地1）：用受控 `site.submit` 挂起响应，断言两条首刀在**任何响应返回前**都已发出，随后两条都 `succeeded`。
2. 时段重叠的两块场地任务（同为 19:00–20:00，场地1/场地2）：同样挂起响应，断言在第一条响应返回前只发出 1 条；放行后第二条才发出，顺序为场1→场2，两条都 `succeeded`。

`npm run check` 通过；`node --test --test-isolation=none --test-concurrency=1 "tests/*.test.ts"` 128 项全部通过。测试使用 FakeSite，无真实创建/取消，实际预约写转发为 0。

注：本机沙箱内 `npm test` 会因测试运行器默认 `spawn` 子进程遇到 `EPERM`（命名管道限制），改用 `--test-isolation=none` 在同一进程内运行，测试内容不变。

## 风险与未验证

- 同账号两条创建请求真正并发，网站是否限流、是否返回新的拒绝形态（“资源分配错误”或误报“当前用户在当前时间有其它会议”），均无真实证据；平台按账号校验的粒度也只验证过“重叠时段被拒”，未验证“相邻时段并发”。
- 建议下一次零点用一条 19:00–19:30 + 一条 19:30–20:00（可同一场地）实测：核对两条 `wireTriggerDelayMs`、首刀间隔是否毫秒级、响应形态、最终网站记录；同时确认同时段两块场地仍按串行发出。
- 出现任何未识别形态仍按既有规则先核对并暂停，不自动重试、不自动取消。
- 两个实例都需要重启并重新“检查登录”后才加载 1.2.21；`data`/`data-b` 未改动。
